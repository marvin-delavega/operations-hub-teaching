# Implementation Plan: History Module
Source PRD: [PRD-history-module.md](PRD-history-module.md)
Date: 2026-07-01

## Summary
Build the admin-only **History** module: two GET-only forks (`/history/replenishment`, `/history/delivery`) that list, filter, and open immutable, self-contained snapshots of committed replenishment runs and delivery sessions. The snapshots are **written by the replenishment and delivery submission use cases inside their existing atomic transactions** — the history module itself never writes. The bulk of the work is (1) new app-owned tables + idempotent `delivery` extensions, (2) enriching the two existing write paths to persist snapshots (including plumbing the decision context / mode settings from the two client pages), and (3) the history read module (domain → application → infrastructure → container → api → page) with list/filter/detail screens, print, and CSV export.

## Decisions

- **Resolved by developer** — *Path mixing when one submission contains both Standard and Stockout lines*: **split into up to two run records by line path** (one `standard`, one `stockout`), each self-contained; a PO that physically mixed lines appears under both runs limited to that run's lines. Keeps the run-header `path` enum as the data model specifies and matches FR-11 (combined list, each record path-tagged). No change to the replenishment submit flow.
- **Resolved by AI — snapshot source is the client payload, not a server recompute.** The whole point of the snapshot (FR-14/16) is to preserve *what the user saw and submitted*. The replenishment submit body is extended to carry each line's decision context (`path`, `orderPeriodDays`, `salesRate`, `sellingAreaDemand`, `sellingAreaNames`, `effectiveAvailable`, `dos`, `suggestedQty`, stockout fields, `unitSymbol`) plus run-level `rounding`, `salesRangeFrom/To`. Server still resolves `item_id`, `supplier_name`, `manufacturer_name`, `location_name` from DB (it already resolves supplier/manufacturer in `createAll`) — those are trusted labels, not decisions.
- **Resolved by AI — `created_by` captured server-side from the session.** [api/po/route.ts](../../app/(authenticated)/replenishment/api/po/route.ts) does not currently read the session; add `auth()` (mirroring [delivery/api/route.ts](../../app/(authenticated)/delivery/api/route.ts)) to obtain `created_by_user_id`; `created_by_name` from `session.user.name`. Same for the receiver name already available on the delivery side.
- **Resolved by AI — delivery per-line snapshot is built server-side inside `commit`.** The commit loop already iterates original PO lines + not-ordered + new items with ordered/received quantities and calls `classifyLine`; write `delivery_line` rows there rather than trusting the client. Only the **mode settings** (`blindDelivery`, `continuousScanning`) must come from the client session snapshot (they live in the delivery page's `sessionBlind` / `sessionContinuous`).
- **Resolved by AI — sub-route naming**: `/history` (fork choice), `/history/replenishment`, `/history/replenishment/[runId]`, `/history/delivery`, `/history/delivery/[deliveryId]` (PRD FR-2 default; stays in the module route group). APIs at `/history/replenishment/api`, `/history/replenishment/api/[runId]`, `/history/delivery/api`, `/history/delivery/api/[deliveryId]` (CLAUDE.md: never `/api/{module}`; `page.tsx` and `route.ts` can't share a dir).
- **Resolved by AI — created-by filter source**: list **only users present in history** (`SELECT DISTINCT created_by_user_id/created_by_name`), per the PRD's stated lean, keeping the picker relevant and avoiding a cross-module users dependency.
- **Resolved by AI — export**: CSV generated **client-side** from the already-loaded detail response (line rows); print uses the rendered summary with a print-oriented layout. No `?format=csv` server variant, no PDF (PRD defers PDF).
- **Assumption** — pagination is **cursor by `(created_at, id)` descending** with a `limit` (default 25); newest-first, no default date window (FR-3). `dos`, `sales_rate`, etc. stored as `DECIMAL(18,4)` to match `item_sales_daily`.
- **Assumption** — the replenishment snapshot is written **after** the POs are minted inside the same `withPoMintRetry` transaction in `createAll`, so each run PO row can store the freshly-minted `po_code`. If `createAll` returns 0 POs (all lines zero-qty), no run is written.

## Data Model (scripts/create-app-tables.sql)

All new tables mirror the file's existing style (InnoDB, utf8mb4_0900_ai_ci, no FK into ActiveOne; FKs only between our own parent/child tables with `ON DELETE CASCADE`, as `delivery_new_items` already does).

**`replenishment_run`** (header) — cols per PRD §6: `id` PK, `path` enum('standard','stockout'), `location_id`, `location_name`, `created_by_user_id`, `created_by_name`, `rounding` enum('up','down'), `sales_range_from` date null, `sales_range_to` date null, `supplier_count`, `po_count`, `line_count`, `created_at` datetime default CURRENT_TIMESTAMP. Indexes: `created_at`, `location_id`, `created_by_user_id`.

**`replenishment_run_po`** (section) — `id` PK, `run_id` (FK → `replenishment_run` ON DELETE CASCADE), `po_code` varchar (indexed for FR-6 search), `supplier_id`, `supplier_name`, `manufacturer_id` null, `manufacturer_name` null. Index `run_id`, index `po_code`, index `supplier_id` (FR-9 supplier filter).

**`replenishment_run_line`** (per-line snapshot, path-discriminated) — `id` PK, `run_po_id` (FK → `replenishment_run_po` ON DELETE CASCADE), `item_id`, `item_description` text, `unit_symbol` varchar, `order_period_days` int, `sales_rate` decimal(18,4), `selling_area_demand` decimal(18,4) null, `selling_area_names` text null, `effective_available` decimal(18,4) null, `dos` decimal(18,4) null, `suggested_qty` int, `final_qty` int, `last_sold_date` date null, `stockout_daily_rate` decimal(18,4) null, `stockout_window_units` decimal(18,4) null, `created_at`. Index `run_po_id`.

**`delivery` (extend, idempotent ALTERs)** — add `location_name` varchar(255) null, `supplier_name` varchar(255) null, `original_po_code` varchar(50) null, `receiver_name` varchar(255) null, `blind_delivery` tinyint(1) not null default 0, `continuous_scanning` tinyint(1) not null default 1. Each guarded by the information_schema `COLUMN_NAME` check + `PREPARE/EXECUTE/DEALLOCATE` pattern already used for `users.employee_code` etc. Add indexes on `created_at`, `location_id`, `supplier_id`, `received_by_user_id`, `original_po_code`, `new_po_code` (idempotent index-exists guard).

**`delivery_line`** (per-line snapshot) — `id` PK, `delivery_id` (FK → `delivery` ON DELETE CASCADE), `item_code` varchar(50), `item_description` text, `ordered_qty` int, `received_qty` int, `status` enum('exact','over','under','not_ordered','new_item'). Index `delivery_id`. (New Items continue to live in the existing `delivery_new_items` — FR-19.)

## Implementation Steps

### A. Database
1. **`scripts/create-app-tables.sql`** — append the four new `CREATE TABLE IF NOT EXISTS` blocks and the idempotent `delivery` `ALTER`/index guards described above. Keep them after the existing `delivery` / `delivery_new_items` blocks so ordering is intuitive.

### B. Replenishment snapshot write path
2. **Extend the payload contract** — [PurchaseOrder.ts](../../app/(authenticated)/replenishment/domain/PurchaseOrder.ts): add optional decision-context fields to `PurchaseOrderLine` (`path: 'standard'|'stockout'`, `orderPeriodDays`, `salesRate`, `sellingAreaDemand`, `sellingAreaNames: string[]`, `effectiveAvailable`, `dos`, `suggestedQty`, `unitSymbol`, `lastSoldDate?`, `stockoutDailyRate?`, `stockoutWindowUnits?`) and run-level fields to `PurchaseOrder` (`rounding: 'up'|'down'`, `salesRangeFrom: string|null`, `salesRangeTo: string|null`, `createdByUserId`, `createdByName`). Keep existing fields; the PO-writing logic ignores the new ones.
3. **Client submit body** — [replenishment/page.tsx](../../app/(authenticated)/replenishment/page.tsx) `handleSubmitPO` (~L703): extend each mapped line with the decision context already present on `POLineState` (add `path`, `dos`, `sellingAreaDemand`, `sellingAreaNames`, stockout fields to `POLineState` where missing — the standard/stockout `buildPO` mappers at ~L609/640 populate them; `path='standard'|'stockout'` set in each mapper) and add run-level `rounding: globalRoundUp?'up':'down'`, `salesRangeFrom/To` from the header range (null on stockout-only lines). `suggestedQty` = `computeSuggestion(...)` at build time.
4. **API session + validation** — [api/po/route.ts](../../app/(authenticated)/replenishment/api/po/route.ts): add `const session = await auth()` (import from `@/app/shared/infrastructure/auth`), reject unauthenticated (401), and pass `createdByUserId`/`createdByName` into the use-case input. Preserve existing field validation; do not add business logic (CLAUDE.md).
5. **Repository writes the snapshot** — [MySQLPurchaseOrderRepository.ts](../../app/(authenticated)/replenishment/infrastructure/MySQLPurchaseOrderRepository.ts) `createAll`: after minting each supplier×manufacturer PO (inside the same `withPoMintRetry` transaction), also **partition that PO's lines by `path`**. For each distinct path present across the whole submission, upsert one `replenishment_run` header (keyed in-memory per path within this call), then per PO write a `replenishment_run_po` row (with the minted `po_code`, supplier/manufacturer snapshot labels) and its `replenishment_run_line` rows for that path's lines. Compute `supplier_count`/`po_count`/`line_count` per run and `UPDATE` the header at the end. Resolve `location_name` via a `SELECT NAME FROM location WHERE ID=?` (pattern from [MySQLLocationRepository.ts](../../app/(authenticated)/location/infrastructure/MySQLLocationRepository.ts)). Because both the ActiveOne POs and the snapshot are in one transaction, a failure rolls back both (FR-20).
   - Keep the write in a private helper (`persistRunSnapshot(conn, ...)`) mirroring the delivery repo's `persistDeliveryRecord` structure to preserve Single-Responsibility.
6. **Use case / container** — `CreatePurchaseOrdersUseCase.execute` signature already takes the whole `PurchaseOrder`; no change beyond the richer type. No new container factory.

### C. Delivery snapshot write path
7. **Commit contract** — [Delivery.ts](../../app/(authenticated)/delivery/domain/Delivery.ts): add `blindDelivery: boolean` and `continuousScanning: boolean` to `DeliveryCommit`; [CommitDeliveryUseCase.ts](../../app/(authenticated)/delivery/application/CommitDeliveryUseCase.ts) `CommitDeliveryInput`: same two fields, threaded through to `repository.commit`.
8. **Client + API** — [delivery/page.tsx](../../app/(authenticated)/delivery/page.tsx) commit body (~L735): add `blindDelivery: blind, continuousScanning`. [delivery/api/route.ts](../../app/(authenticated)/delivery/api/route.ts): parse/coerce the two booleans from the body and pass into the use case (already reads the session for `receiverUserId`).
9. **Repository writes line + header snapshot** — [MySQLDeliveryRepository.ts](../../app/(authenticated)/delivery/infrastructure/MySQLDeliveryRepository.ts): while iterating `originalLines`, not-ordered lines, and new items in `commit`, accumulate `delivery_line` rows (`item_code`, `item_description`, `ordered_qty`, `received_qty`, `status` from the existing `classifyLine` call — map `over_served`→`over`, `under_served`→`under` to the enum). In `persistDeliveryRecord`: resolve `location_name` (`SELECT NAME FROM location`), `supplier_name` (`SELECT NAME FROM contact WHERE ID=VENDOR_ID` — already joined elsewhere), `receiver_name` (`SELECT name FROM users WHERE id=?`), store `original_po_code` (`original.CODE`), `blind_delivery`, `continuous_scanning`, and insert the accumulated `delivery_line` rows. ## Risks & Open Questions
- **Payload growth / trust boundary.** The replenishment submit body now carries decision context. The server must still resolve `item_id` and labels itself (never trust client SKUs→IDs) and must ignore client-sent values for anything that drives the ActiveOne PO (qty/rate). Verify the enriched body stays within request-size limits for large runs (hundreds of lines) on Android tablets.
- **Two-run split correctness.** When a submission mixes paths, confirm `supplier_count`/`po_count`/`line_count` are computed **per run** (per path), and that a physically-mixed PO's `po_code` correctly appears under both runs limited to that run's lines. Add a manual check against a mixed submission after implementation.
- **`dos` for stockout lines.** Stockout `POLineState.effectiveAvailable = 0`; store `dos`/`effective_available` as null for stockout lines (FR-16) rather than 0, so the detail view can distinguish "no DOS context" from "0 days".
- **Existing `delivery` rows.** Rows created before this change lack the new snapshot columns (null names, null `original_po_code`, default mode flags). The detail view must tolerate nulls (show blanks, never error) — matches FR (renamed/removed entity) handling.
- **Manila date boundaries in SQL.** `created_at` is stored server-local/UTC; date-range filters are Manila dates. Confirm the boundary conversion (shift by +8h or compare against `CONVERT_TZ`) is consistent with how `manilaToday` and the rollup module already treat Manila, to avoid off-by-one on range edges (FR-10).
- **Transaction size.** The replenishment snapshot adds several inserts inside `withPoMintRetry`'s transaction; ensure the retry-on-mint-collision path re-runs the snapshot writes cleanly (they are keyed to freshly-minted PO ids each attempt, so a retry naturally recomputes them — verify no duplicate rows leak across attempts).
